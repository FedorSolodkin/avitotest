# Кандидатогенерация для категории «Услуги» (Авито)

Тестовое задание: по поисковому запросу найти в корпусе из ~189 тыс. объявлений до 50
подходящих (кандидатогенерация, метрика — Recall@50).

## Данные

Три файла в формате Parquet (скачиваются по ссылке из условия задания, в репозиторий не
включены — слишком большие):

- `train.parquet` — 497 673 пары «запрос → объявление, которое выбрал пользователь»;
- `benchmark_queries.parquet` — 2452 запроса без разметки;
- `benchmark_items.parquet` — корпус из 189 212 объявлений, среди которых нужно искать.

Файлы нужно положить в папку `data/` рядом со скриптами.

## Подход

Задача решается в два этапа — сначала широкая кандидатогенерация, потом более точное
переранжирование, как это обычно устроено в реальном поиске:

**1. Кандидатогенерация.** Для каждого запроса из всего корпуса отбирается пул из
~1–2 тыс. кандидатов — объединение топов по пяти независимым источникам похожести:

- TF-IDF по словам и по символьным n-граммам (заголовок и «тело» объявления —
  заголовок + параметры + начало описания). N-граммы нужны, чтобы ловить опечатки и
  словоформы, которые не совпадают по словам;
- TF-IDF между запросом и историей запросов, по которым объявление уже выбирали в train
  («doc expansion» — если объявление раньше выбирали по запросу «массаж спины», это
  сильный сигнал, даже если само объявление слова «спина» не содержит);
- косинусная близость плотных эмбеддингов запроса и объявления (модель
  `intfloat/multilingual-e5-small`, открытая, крутится локально на CPU);
- априорная вероятность локации объявления при данной локации поиска, оценённая по train.

**2. Переранжирование.** Из пула кандидатов топ-50 выбирает модель LightGBM
(`lambdarank`). Кроме самих скоров этапа 1, ей на вход идут: относительный ранг и
величина каждого скора внутри запроса, совпадение локации, пересечение фильтров поиска с
параметрами объявления, прямое пересечение слов запроса с текстом объявления, доля
«типичной» подкатегории среди топ-50 по базовому скору, а также статические признаки
объявления (рейтинг, число отзывов, цена).

## Локальная валидация

Разметки у бенчмарка нет, поэтому для отладки строится локальная валидация из train
(`prepare_data.py`). Важный момент: наивная валидация (случайный срез train) сильно
завышает качество, потому что запросы бенчмарка в основном («хвостовые») почти не
встречаются в train — 63% вообще не пересекаются, у остальных медианная частота
встречаемости — 3 раза, — тогда как случайные запросы train встречаются в среднем в
десятки раз чаще. Из-за этого признак «история выбора» на наивной валидации выглядит
намного сильнее, чем есть на самом деле.

Поэтому валидация строится так, чтобы имитировать это распределение: часть запросов
исключается из train полностью, часть оставляется редкой (не больше 30 повторов).

| Версия | Recall@50 (локальная валидация) |
|---|---|
| только TF-IDF, без подбора весов | 0.813 |
| TF-IDF, веса подобраны на «лёгкой» валидации | 0.914 |
| TF-IDF + эмбеддинги, честная (хвостовая) валидация | 0.870 |
| + LightGBM-ранкер | 0.895 |
| + прямые лексические признаки (пересечение слов) | **0.900** |

Разница между первой (0.914) и переделанной (0.870) валидацией на одном и том же наборе
сигналов — это и есть цена того, что наивная валидация не отражает реальное распределение
бенчмарка.

## Структура репозитория

```
prepare_data.py       — очистка текстов объявлений, подготовка train-пар, локальная валидация
compute_embeddings.py — эмбеддинги объявлений и запросов (multilingual-e5-small)
build_candidates.py   — кандидатогенерация (TF-IDF + эмбеддинги + локация) -> пул кандидатов
train_and_predict.py  — LightGBM-ранкер, локальная кросс-валидация, предсказание на бенчмарке
check_answer.py       — проверка answer.csv на соответствие формату задания
answer.csv            — итоговый ответ
```

## Как воспроизвести

```bash
pip install -r requirements.txt

python prepare_data.py
python compute_embeddings.py       # при первом запуске скачает веса модели с Hugging Face
python build_candidates.py val
python build_candidates.py bench
python train_and_predict.py
python check_answer.py answer.csv
```

Всё считается локально на CPU, без обращений к внешним API (кроме одноразовой закачки
весов модели эмбеддингов при первом запуске).

## Библиотеки и модели

- `pandas`, `numpy`, `scipy` — обработка данных;
- `scikit-learn` (`HashingVectorizer`, `TfidfTransformer`) — TF-IDF признаки;
- `sentence-transformers` + модель `intfloat/multilingual-e5-small` (открытая,
  разворачивается локально) — плотные текстовые эмбеддинги;
- `lightgbm` — ранжирующая модель (`lambdarank`).

## Ограничения и риски

- Кандидатный пул покрывает около 98% релевантных объявлений — это верхняя граница,
  выше которой второй этап (ранжирование) прыгнуть не может;
- локальная валидация — это имитация распределения бенчмарка, а не точная копия, поэтому
  итоговый результат на бенчмарке может отличаться от локальной оценки;
- признак «история выбора объявления в train» работает слабее на запросах, которых в
  train не было вовсе (63% бенчмарка) — именно поэтому в модель добавлены эмбеддинги и
  прямые лексические признаки, которые не зависят от истории.
